# 프로젝트 개발 노트

프로젝트를 진행하며 다룬 문제와 선택, 결과의 해석을 짧게 정리했습니다. 2026-10-09에 확인한 공개 기록을 바탕으로 Codex가 작성한 요약이며, 당시의 개인적인 감정이나 기록에 없는 판단 이유를 덧붙이지 않았습니다. 아래 근거는 확인한 버전에 고정되어 있습니다. 이후 진행 상황은 각 프로젝트 저장소에서 확인할 수 있습니다.

## FabGuard AI

### 합격 판정보다 점검 순서를 다룬 이유

FabGuard의 출발점은 점검할 수 있는 생산 건수가 제한됐을 때 무엇부터 살펴볼지 정하는 것이었습니다. 최희찬은 UCI SECOM을 활용할 주제와 초기 실험 계약, 활용 범위를 제시했고, Codex가 전처리·모델 비교·평가 코드와 결과 문서를 작성하고 실행했습니다.

V1의 선택 모델은 시간순 평가 구간에서 0.5 임계값으로 Fail 24건을 하나도 찾아내지 못했습니다. 같은 모델의 점수를 순서로 사용하면 상위 40건에서 5건을 포착했습니다. 이는 순위에 일부 신호가 있다는 결과입니다. 다만 임계값 하나의 실패로 모든 분류 방식이 부적합하다고 결론 내릴 수는 없습니다.

이 사례에서 구분할 것은 모델 점수와 사용 목적입니다. 상위 일부를 먼저 검토하게 하는 것과 합격 여부를 자동 판정하는 것은 요구하는 근거가 다릅니다. 최희찬은 결과의 해석 범위와 공개 내용을 검토했습니다.

V1은 교차검증보다 시간순 평가 성능이 낮았고, 개발 중 holdout 노출도 기록되어 있어 provisional 상태입니다. 실제 제조 수율 개선을 입증한 결과로 확대하지 않습니다.

## Bunkering AI

### 보상이 가장 높은 정책을 비용 절감으로 설명하지 않은 이유

초기 고정 급유와 가격 반응형 규칙은 공식 비교에서 각각 100회와 97회 연료 고갈로 끝났습니다. 연료를 유지하며 도착하는 단순 정책도 비교할 수 있도록 안전재고 규칙이 추가됐습니다. 최희찬은 요구사항과 실험 방향을 정하고 결과를 검토했으며, 이현수는 Safe Stock의 Windows 독립 재현과 관련 PR 병합을 맡았습니다. 구현에는 AI 도구의 지원이 있었습니다.

2026-09-01 공식 평가에서는 단일 학습 seed 42의 Double DQN과 규칙 3종을 평가 seed 42~141의 100개 항해 조건에서 비교했습니다. DQN과 안전재고 규칙은 모두 도착했지만, DQN의 평균 급유 행동은 5.31회, 안전재고는 1회였습니다. 합성 비용지수도 각각 약 847,118과 545,393이었습니다.

보상은 DQN이 높았습니다. 그러나 당시 보상은 구매량과 구매비용을 직접 반영하지 않았습니다. 따라서 보상 순위만으로 비용 절감 효과를 설명할 수 없었습니다. 목표로 삼은 지표가 실제 원하는 행동과 맞는지 함께 확인해야 한다는 사례입니다.

이 글은 위 공식 평가의 해석을 다룹니다. 합성 비용지수는 실제 화폐 비용이 아니며, 이후의 다중 seed 평가나 후속 계획기 결과와 섞지 않습니다.

## Adversarial AI Security

### 내 PC에서 맞았다는 결과와 외부 재현을 구분하기

모델을 다시 실행해 같은 결과를 얻었는지 확인하려면 비교 범위부터 정해야 합니다. 원본 이미지가 같은지, 예측 라벨이 같은지, 확률값까지 같은지는 서로 다른 검사입니다.

최희찬은 검증 범위와 통합 조건을 정하고, Windows PC에서 원본 이미지 781장과 로컬 모델로 검증을 실행했습니다. 가우시안·평균 필터 비교 실험의 원본 결과 파일도 제공했습니다. Jules는 연구근거 감사 도구를 구현했고, Codex는 추가 검토·보완과 결과 재계산을 지원했습니다. 팀원의 시각 검토는 별도 기여로 기록되어 있습니다.

공식 저장소의 2026-10-01 기록에서는 연구 수행 PC의 전체 재실행을 LOCAL_PASS로, 외부 독립 검증은 기존 FAIL로 구분했습니다. 로컬에서 예측 라벨과 요약 지표가 일치해도 외부 실행의 14장·16개 예측 차이가 해결됐다는 뜻은 아니기 때문입니다. 확률 벡터는 해당 로컬 비교 대상에서 제외됐습니다.

이 사례의 핵심은 통과 여부에 환경과 비교 대상을 함께 붙이는 것입니다. 이번에 확인한 공식 저장소 기준으로 환경 간 차이의 단일 원인은 미확정이며, 개인 포크의 후속 작업이 공식 결과에 반영됐다고 간주하지 않습니다.

## TriGuard AI

### 화면에 숫자를 표시한 뒤 원자료와 다시 대조하기

여러 기관의 통계를 묶으면 숫자를 보여주는 것뿐 아니라 그 숫자가 어떤 지역과 기간을 뜻하는지도 설명해야 합니다. 같은 지방청이 여러 시·도를 담당할 때, 지방청 전체 수치를 개별 지역 수치로 읽을 여지가 있었습니다.

최희찬은 지도와 통합 관할 동작의 차이를 지적하고, 원자료 안내와 강의에서 다룬 검증 원칙의 적용을 요청했습니다. Codex는 화면·검증기·CI·오류 사례 테스트를 작성했습니다. 이 역할 구분은 요구사항–검증 연결표에 남아 있습니다.

공개 통계 화면에서는 원본 해시, 중복·누락, 표시 수치, 전국 합계와 다운로드 CSV를 검사하도록 연결했습니다. 병역판정검사 보관 자료의 경우 105행·630개 수치와 42개 전국 합계가 대조 대상입니다. 검증 실패 시 새 배포 산출물을 만들지 않도록 했습니다.

여기서 확인한 것은 정의한 항목이 보관 원자료와 맞는지입니다. 원자료 자체의 정확성이나 최신성, 위험점수의 미래 예측력까지 증명한 것은 아닙니다. 검사 항목과 통과 범위를 함께 보여주는 것이 이 작업의 핵심입니다.

## Judicial AI Safety Lab

### 응답 파일이 생겼다고 자료 수집 성공은 아니었다

공식 판례 자료를 수집한 PC 실행에서 검증의 빈틈이 드러났습니다. 유효하지 않은 인증값으로 받은 API 오류 응답도 이전 수집기가 해시를 만들고 수집 자료로 집계했습니다. 파일이 저장됐고 해시가 있다는 사실만으로 내용이 정상 판례 자료임을 보장하지 못한 것입니다.

최희찬은 연구 범위와 다른 프로젝트에서 가져올 검증 방법을 정하고, 노트북의 Anaconda 환경에서 자료 수집·검증을 실행했습니다. 실행 중 드러난 문제에 대해 AI 지원으로 검증 로직을 보완하고 결과를 검토했습니다.

v12에서는 판례 상세 객체와 필수 식별정보를 확인하고, 요청한 판례 번호와 응답 번호가 일치해야 수집 결과로 인정하도록 바뀌었습니다. 오류·빈 응답·상세자료가 아닌 응답은 실패로 기록합니다. 이후 v13 기록에는 30건의 상세자료 대조와 평가 전 검사를 통과한 상태가 남아 있습니다.

이 과정에서는 수집 성공, 자료 검증, 평가 준비, 전문가 검토를 별도 단계로 관리했습니다. 자료 30건을 준비했다는 사실은 법률 판단이 정확하다는 결과가 아닙니다. 사람의 검토와 그 근거는 별도로 필요합니다.
